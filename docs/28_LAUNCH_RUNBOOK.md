## 2. قرارات المالك المُثبتة (لا تُعاد مناقشتها دون طلبه)

- **الخطة المجانية فقط** — رُفض خيار Workers ‏المدفوع صراحةً («عاوزه حل مجاني مش عاوز اي حاجه بفلوس»).
- **مصادقة خارجية مجانية للهوية** — ‏Google، كاستثناء ضيّق من قاعدة «لا خدمات تشغيل خارجية» للمصادقة فقط.
- **التسجيل العام بالبريد + كلمة المرور مفتوح ومجاني** (`ALLOW_PUBLIC_SIGNUP = "true"`) — قرار 2026-10-30 (أُلغي إغلاق التسجيل).
- **اشتقاق على طبقتين** بدل رفع تكرارات الخادم: ‏600k ‏في المتصفح (‏WebCrypto، مجاني) + ‏30k ‏على الخادم مع pepper
  ⇒ ‏≥630k ‏لكل تخمين. لا يُرفع `PBKDF2_ITERATIONS` فوق ‏30k ‏على الخطة المجانية (‏94ms ‏تتجاوز حد ‏CPU ‏10ms ‏فيُقتل الطلب).
- **لا حذف ولا إعادة رفع للمستودع** لإصلاح ‏CI؛ لا تغيير لبيانات الإنتاج أو الأسرار دون إذن صريح.

## 4. إعداد الإنتاج — ملف مستقل `wrangler.production.toml` (2026-10-28)

**لا يُضاف قسم `[env.production]` إلى `wrangler.toml` الملتزَم.** بوابة الجاهزية
تقرأ `[env.production.vars]` أولًا عند غياب `--env`، واختبار
`tests/deploy-preflight.test.ts` يثبت أن `wrangler.toml` الحالي يجب أن يفشل
البوابة بأكواد التطوير — إضافة قسم إنتاج إليه ستكسر هذا الحارس الصامت. لذلك
الإنتاج في ملف مستقل لا يقرأه `wrangler` تلقائيًا، ولا ينشر به إلا أمر صريح
بـ`--config`. لا اختبارات ولا أدوات في المستودع تفحص ملفات `*.toml` أخرى،
فالملف المستقل آمن من الفحص التلقائي.

الملف يحمل القيم المعروفة فقط (`ENVIRONMENT = "production"`،
`ALLOW_PUBLIC_SIGNUP = "true"`، `CLIENT_KDF_REQUIRED = "true"`، `CLIENT_KDF_ITERATIONS = "600000"`، `PBKDF2_ITERATIONS = "30000"`،
`SESSION_TTL_DAYS = "30"`، الاسم والتوافق والأصول وربط D1 بالاسم `es-ar-prod`)،
والقيم الناقصة **محذوفة عمدًا لا مخترعة**: لا سطر `database_id`، ولا
`APP_ORIGIN`، ولا `GOOGLE_CLIENT_ID`، ولا أي سر. فحصه الحالي (موثّق بتشغيل
فعلي 2026-10-28): **FAIL (خروج 1)** — خطآن (`APP_ORIGIN_MISSING`،
`D1_ID_MISSING`) + حاجز `KDF_BELOW_OWASP` + ‏0 تنبيهات. هذا هو الوضع الصحيح
قبل أن يضيف المالك قيمه؛ أي PASS الآن كان سيعني قيمة مخترعة.

`MEDIA_ORIGIN` محذوف عمدًا أيضًا: الـWorker لا يستهلكه (مُعلن في الأنواع فقط)،
ومتغيّر البناء `VITE_MEDIA_ORIGIN` غير مضبوط أصلًا، وكل مفاتيح الصوت `pending/`
فيغطيها TTS المتصفح. ليس حاجب إطلاق.

### 4.1 جدول القيم التي يضيفها المالك بنفسه (لا شيء منها يُرسل في الشات)

| القيمة | كيف تُحصل عليها | أمر/موضع الضبط |
| --- | --- | --- |
| النطاق الإنتاجي | إما نطاق `workers.dev` مجاني يُكشف عند أول نشر (`<name>.<subdomain>.workers.dev`)، أو دومين خاص يُربط في لوحة Cloudflare ← Workers ← Domains | سطر واحد في `wrangler.production.toml` بصيغة `https://` فقط، بلا أصول محلية مختلطة (انظر §9) |
| معرّف قاعدة الإنتاج | من لوحة Cloudflare ← D1 بعد الإنشاء، أو من مخرجات `wrangler d1 create es-ar-prod` | سطر `database_id` داخل `[[d1_databases]]` في `wrangler.production.toml` |
| عميل Google OAuth | Google Cloud Console ← Credentials ← Create OAuth client ID ‏(Web)؛ الـRedirect ‏URI ‏للإنتاج: `https://<النطاق>/api/auth/oauth/google/callback`، وللتجربة المحلية: `http://127.0.0.1:8787/api/auth/oauth/google/callback` | الـClient ID (علني) سطر في `wrangler.production.toml` أو متغيّر بيئة؛ **السر لا يُرسل في الشات أبدًا** |
| `PASSWORD_PEPPER` | يولّده المالك محليًا (‏≥32 ‏حرفًا عشوائيًا) | `npx wrangler secret put PASSWORD_PEPPER --config wrangler.production.toml` — إلزامي؛ بدونه المصادقة 503 |
| `GOOGLE_CLIENT_SECRET` | من عميل Google OAuth نفسه | `npx wrangler secret put GOOGLE_CLIENT_SECRET --config wrangler.production.toml` |
| توكن Cloudflare للنشر | لوحة Cloudflare ← My Profile ← API Tokens ← Create Custom Token (‏Workers Scripts: ‏Edit ‏+ D1: ‏Edit ‏فقط) — **التوكن القديم المُرسل في الشات مكشوف ويجب حذفه** | متغيّر بيئة محلي `CLOUDFLARE_API_TOKEN` وقت النشر فقط، أو `wrangler login` بتدفق الجهاز — لا يُحفظ في ملف |

بعد إضافة القيم، فحص البوابة المتوقع على الملف الإنتاجي:

```bash
node tools/check-deploy-ready.mjs --file wrangler.production.toml
# المتوقع الصادق: 0 أخطاء + BLOCKED (KDF) بخروج 2 — الوضع المقبول الموثّق في §2.
# أي خطأ آخر = توقف. وفحص wrangler.toml الافتراضي يبقى FAIL كما هو (حارس التطوير).
```

## 5. خطوات النشر بالترتيب (بعد اكتمال §3 + التصريح)

```bash
# 0) في مساحة العمل هذه، الـCLI المورَّد هو:
WRANGLER="node tools/wrangler-env/node_modules/wrangler/wrangler-dist/cli.js"

# 1) المصادقة: تدفق جهاز wrangler login، أو CLOUDFLARE_API_TOKEN في البيئة فقط
$WRANGLER login

# 2) إثبات المسار البعيد على قاعدة تجريبية أولًا (يتطلب مصادقة wrangler — انظر §11)،
#    ثم قاعدة الإنتاج + الترحيلات 0001–0005 بالترتيب مع تتبّع SHA-256 في جدول
#    schema_migrations (نفس ما يفعله tools/db.mjs محليًا؛ وهو يرفض --remote
#    بالتصميم، فتُطبَّق الترحيلات على الإنتاج بالأوامر الصريحة في §11.3 بعد
#    نجاح الإثبات التجريبي، وتُتحقق من عدد الجداول (62) قبل أي استيراد).
#    استيراد المحتوى إلى الإنتاج: بملف SQL المصدَّر (§11.2) — لا يُرتجل.
$WRANGLER d1 create es-ar-prod

# 3) الأسرار (§4.1) ثم فحص البوابة على ملف الإنتاج الحقيقي
node tools/check-deploy-ready.mjs --file wrangler.production.toml
# المتوقع الصادق: 0 أخطاء + BLOCKED (KDF) بخروج 2 — هذا هو الوضع المقبول الموثّق،
# لا PASS كاملًا على الخطة المجانية مع مسار كلمة المرور.

# 4) البناء والنشر (فقط بعد التصريح الصريح) — بملف الإنتاج المستقل، لا --env:
npm run build
$WRANGLER deploy --config wrangler.production.toml

# 5) تحقق ما بعد النشر: /api/health، التسجيل العام مغلق، دخول Google،
# فتح درس وحفظ تقدم، ثم تشغيل الدخان والمتصفح ضد النطاق الإنتاجي.
```

## 6. بوابة ما قبل النشر — القراءة الصحيحة

- على `wrangler.toml` الحالي: **FAIL ‏(خروج ‏1)** — ‏3 أخطاء (`NOT_PRODUCTION`، ‏`APP_ORIGIN_LOCAL`،
  ‏`D1_ID_PLACEHOLDER`) + حاجز ‏KDF ‏+ تنبيه ‏HTTPS. هذا هو السلوك الصحيح، لا عطل.
- على ملف الإنتاج المستقل `wrangler.production.toml` بعد إضافة قيم المالك: المتوقع
  **BLOCKED ‏(خروج ‏2)** بسبب ‏KDF ‏فقط — مقبول بموجب §2 (مستخدمو ‏Google ‏الجدد
  بلا كلمات مرور، والتسجيل العام مغلق). أي خطأ آخر = توقف. وقبل إضافة القيم:
  ‏FAIL ‏(خروج ‏1) بخطأي `APP_ORIGIN_MISSING` و`D1_ID_MISSING` — انظر §4.

## 7. فجوات صريحة قبل الإطلاق (ليست حواجز خفية)

1. **التنفيذ البعيد ما زال يحتاج مصادقة.** مسار القاعدة التجريبية البعيدة
   مكتمل ومثبَت محليًا (§11: ترحيلات + تصدير محتوى + تحقق + إعادة تطبيق بلا
   تكرار)، لكن تشغيله عن بُعد يتطلب `wrangler login` أو توكنًا صالحًا — غير
   موجود في بيئة التطوير هذه (`whoami: not authenticated`)، والسكربت يفشل
   سريعًا قبل إنشاء أي شيء. لا يُتجاوز هذا بتوكن يُرسل في الشات.
2. **إنشاء الحساب الإداري الأول — محلول محليًا، والترقية الإنتاجية موثّقة.**
   `tools/admin-create.mjs` ينشئ `super_admin` محليًا فقط (انظر §10)؛ وفي
   الإنتاج: دخول أول عبر ‏Google ‏(ينشئ حساب متعلّم) ثم ترقية مباشرة (§10.2).
   لا فتح مؤقت للتسجيل، ولا إدراج صفوف يدوية ببصمات مخترعة.
3. **النشر البشري للمحتوى:** كل الدروس ‏draft ‏غير مراجَعة. النشر يتم عبر
   `tools/publish-lesson.mjs` (§12) الذي يطبّق البوابات الآلية ثم مسارات
   ‏review/publish ‏في ‏API ‏بعد مراجعة بشرية موثّقة لكل درس (‏spanishReviewer ‏+ translationReviewer ‏من المراجعين أنفسهم) —
   لا نشر جماعي بلا مراجعة، ولا أسماء مفبركة، ولا تجاوز للبوابة بصمت.
4. **حدود موثّقة باقية:** تصميم ‏offline ‏غير منفّذ (طابور تقييمات المراجعة في ‏localStorage ‏فقط)؛
   ‏`review_schedule` ‏PK ‏كامن؛ ‏`minutes_total`/`words_stable` ‏لا تُكتب (غير معروضة)؛ الإنجازات ‏seed-only؛
   لا تحقق بالبريد ولا استرداد كلمة مرور؛ ‏1,225 ‏قيمة ‏audioKey ‏بـ`pending/` ‏في الدروس
   (بلا صوت مُنتَج — ‏TTS ‏المتصفح يغطيها)؛ ‏112 ‏درسًا بلا سيناريو حواري.
5. **الملف النموذجي `content/exemplars/lesson-prea1-hola-me-llamo.json`** أقدم من المسودة
   ويختلف عنها في التمارين؛ الخادم يقدّم المسودة، والاختبارات تقرأ من المسودات.
   أي تعديل مستقبلي يكون على المسودة، لا على العينة.

## 9. قواعد CORS والكوكي وإعادة التوجيه (موثّقة من `src/worker/lib/http.ts`، 2026-10-28)

هذه القواعد هي ما يجعل قيمة `APP_ORIGIN` الإنتاجية حرجة — لا تخمين فيها:

- **CORS — قائمة سماح بالمطابقة التامة فقط.** الأصول المسموحة هي قائمة
  `APP_ORIGIN` مفصولة بفواصل، والمطابقة `includes` تامة (لا wildcards ولا
  سلاسل جزئية). رؤوس CORS تُرسل فقط عندما يطابق `Origin` القادم أحد الأصول:
  `Access-Control-Allow-Origin` = الأصل نفسه، و`Allow-Credentials: true`،
  والطرق `GET/POST/PATCH/DELETE/OPTIONS`، والرأس `Content-Type`،
  و`Max-Age: 600`، و`Vary: Origin`. أصل غير مدرج = لا رؤوس CORS = المتصفح
  يرفض الاستجابة لطلبات الواجهة.
- **حماية CSRF — ثلاث طبقات.** (1) كوكي الجلسة `SameSite=Lax` مع بادئة
  `__Host-` على HTTPS. (2) فحص `Origin` / `Sec-Fetch-Site` على الطرق المغيّرة
  للحالة (`POST/PUT/PATCH/DELETE`): قيمة `cross-site` مرفوضة قطعًا، و`same-origin`
  مقبولة، و`Origin` يُفحص ضد قائمة السماح، وغياب الرأسين معًا يُعامل كعميل
  غير متصفح (مقبول، ويبقى المصادقة مطلوبة). (3) الطلبات المغيّرة للحالة
  ذات الجسم تتطلب `Content-Type: application/json` وإلا `415`.
- **كوكي الجلسة.** الاسم `__Host-ses` عندما يكون الطلب آمنًا فعلًا (رابط `https`،
  أو `X-Forwarded-Proto: https`، أو `CF-Visitor` بمخطط `https`)، وإلا `ses`.
  السمات: `Path=/`، و`HttpOnly`، و`SameSite=Lax`، و`Max-Age = SESSION_TTL_DAYS`،
  و`Priority=High`، ويُضاف `Secure` عند الأمان. القراءة تقبل `__Host-ses`
  دائمًا، وتقبل `ses` على الطلبات غير الآمنة فقط (مرفوضة على HTTPS — مضاد
  لتثبيت الجلسة). تسجيل الخروج يمسح الاسمين؛ والإبطال الحقيقي من الخادم.
- **HTTPS فقط عندما تكون كل الأصول `https://`.** دالة `isHttpsOnly` صحيحة فقط
  عندما يبدأ *كل* أصل مهيّأ بـ`https://` — قائمة مختلطة (`http` + ‏`https`)
  تعطّل بصمت `Secure` وبادئة `__Host-` وHSTS. وHSTS يُرسل فقط عندها، ورأس
  `X-Frame-Options: DENY` في الإنتاج فقط (يُزال في غير الإنتاج لسماح معاينة
  التضمين). بقية الرؤوس ثابتة: `nosniff`، و`strict-origin-when-cross-origin`،
  و`Permissions-Policy` (الميكروفون للذات فقط، والكاميرا/الموقع/الدفع/USB
  مرفوضة)، و`Cross-Origin-Opener-Policy: same-origin`، و`Cross-Origin-Resource-Policy:
  same-origin`، و`X-Permitted-Cross-Domain-Policies: none`.
- **النتيجة العملية للإنتاج:** `APP_ORIGIN` = أصل الإنتاج وحده بصيغة HTTPS
  (يُنصح بأصل واحد). أي أصل ثانٍ (مثل نطاق معاينة) يجب إدراجه صراحةً
  بالصيغة نفسها، وإلا رُفضت طلباته. لا تخلط `http://localhost` مع أصل
  الإنتاج في القائمة نفسها.
- **إعادة توجيه Google OAuth.** رابط الـcallback يُشتق من أصل الطلب نفسه
  (`{APP_ORIGIN}/api/auth/oauth/google/callback`) ويُشترط وجوده في `APP_ORIGIN`
  وإلا فشل مغلقًا. لذلك الـRedirect URI المسجّل في Google يجب أن يطابق أصل
  الإنتاج حرفيًا (انظر §3/§4.1)، وأي تغيير للنطاق يستلزم تحديثه في Google
  أولًا.

### 10.2 في الإنتاج — دخول Google ثم ترقية (بلا كلمات مرور إطلاقًا)


## 11. القاعدة البعيدة: إثبات تجريبي ثم تطبيق الإنتاج

### 11.1 الأدوات

- `tools/export-content-sql.mjs --out <path> [--manifest <path>]` — يولّد ملف
  ‏SQL ‏واحدًا من نفس خطة المستورِد (نفس الدوال، نفس الترتيب، نفس تسلسل
  الإصدارات). كل الأوامر ‏upserts ‏بمعرّفات ثابتة — إعادة التطبيق آمنة بلا
  تكرار. كل الصفوف ‏draft/unreviewed. بلا ‏BEGIN/COMMIT ‏(التطبيق عن بُعد
  يُقسَّم دفعات، والتحقق اللاحق هو شبكة الأمان). أسطر الفاصل تعليقات ‏SQL
  صالحة تتيح التقسيم دون كسر الأوامر متعددة الأسطر.
- `tools/remote-scratch-setup.mjs` — المنسّق: مصادقة ← إنشاء ← ترحيلات
  بترتيبها مع تتبّع ‏checksums ‏← تصدير المحتوى ← تطبيق بدفعات ← تحقق
  (أعداد + روابط ‏2120 ‏مخططة بلا مفقود). الحواجز: الاسم يجب أن يطابق
  ‏`es-ar-scratch(-...)` ‏وبلا ‏`prod` ‏إطلاقًا — لا يمكنه مخاطبة قاعدة
  إنتاج؛ والحذف يتطلب ‏`--teardown` ‏صريحًا فقط.

### 11.2 الإثبات التجريبي (يُشغَّل أولًا، بعد المصادقة)

```bash
# فحص سريع بلا تنفيذ:

# التنفيذ الكامل ثم التحقق (دفعات 40 أمرًا — الحجم المثبت في المستورِد المحلي؛
# توقّع آلاف استدعاءات wrangler، فشغّله كعملية خلفية):
node tools/remote-scratch-setup.mjs --database es-ar-scratch-20261028
# بعد التحقق والفحص، الحذف:
node tools/remote-scratch-setup.mjs --teardown --database es-ar-scratch-20261028
# الإثبات المحلي (بلا شبكة إطلاقًا — نفس الخطوات على ملف SQLite):
node tools/remote-scratch-setup.mjs --local-test --db-file /tmp/scratch.db
```

الإثبات المحلي موثّق بتشغيل فعلي (2026-10-28): ترحيلات ‏5/5، ‏258 ‏درسًا /

تطبيق كاملة بالأعداد نفسها (بلا تكرار). الفارق بين ‏2120 ‏(المخططة)

## 12. نشر الدروس: بوابات آلية + اعتماد بشري (لا تجاوز)

```bash
# معاينة بلا أي طلب (لا كوكي ولا أسماء مطلوبة):
node tools/publish-lesson.mjs --slug prea1-abecedario --dry-run
# النشر الحقيقي — الخادم المحلي يعمل، والكوكي لجلسة مراجع/مدير أعلى:
PUBLISH_SESSION_COOKIE='ses=...' node tools/publish-lesson.mjs --slug prea1-abecedario \
  --spanish-reviewer "الاسم الحقيقي لمراجع الإسبانية" \
  --translation-reviewer "الاسم الحقيقي لمراجع الترجمة"
# أو: --cookie-file <ملف بسطر واحد بقيمة ترويسة Cookie> (تُقرأ ولا تُطبع ولا تُسجَّل)
```

- **البوابات قبل أي طلب:** ملف الدرس موجود وحالته الملفية ‏draft؛ صفر
  أخطاء تدقيق منسوبة للدرس (التنبيهات تُعرض ولا تمنع)؛ والفحوص الشاملة
  سالكة (‏validate-content ‏+ ‏check-content-integrity ‏+ ‏check-curriculum).
  أي فشل = توقف قبل أي طلب شبكة.
- **المسار:** ‏POST `/api/admin/lessons/:slug/review` ‏(يتطلب
  ‏`content.review_es` ‏مركزيًا + ‏`content.review_ar` ‏داخل المعالج، واسمَي
  المراجعين غير فارغين ≤80 ‏حرفًا، ويُسجَّلان في ‏`admin_audit_logs` ‏مع
  ‏reviewedAt) ‏ثم ‏POST `.../publish` ‏(يتطلب ‏`content.publish` ‏و`review_state='approved'` ‏وإلا ‏409). النشر ينشر أسلاف الدرس (الوحدة والبرنامج) معه.
- **لا أسماء مفبركة ولا افتراضية إطلاقًا:** بلا اسمَي مراجعين حقيقيين من
  المراجعين أنفسهم لا نشر — الأداة ترفض، والـWorker ‏يرفض ‏400. الأداة
  محلية فقط (‏http://127.0.0.1 ‏أو ‏localhost) — أي أصل آخر مرفوض قبل أي
  طلب. الاختبارات `tests/publish-lesson.test.ts`: ترتيب الطلبات، فشل
  الاعتماد يمنع النشر، ‏dry-run ‏بلا طلبات، ورفض الدرس الفاسد.
- **لم يُنشر أي درس فعليًا حتى الآن** (‏0 ‏سجلات اعتماد/نشر في تدقيق القاعدة
  المحلية بعد إثبات حي سلبي: ‏400 ‏بلا أسماء، ‏409 ‏بلا اعتماد، ‏403 ‏لمتعلّم).
  أول نشر حقيقي يحتاج اسمَي مراجعين يحددهما المالك بعد مراجعة بشرية فعلية.

## 13. حاجز KDF — التأثير الفعلي على مسارات الإطلاق (بلا تغييرات)

القياس الموثّق `reports/kdf-benchmark.md` ‏(workerd ‏محلي، ‏2026-10-27):
‏PBKDF2-SHA256 ‏عند ‏30,000 ‏تكرارًا = ‏7ms ‏وسيط (‏5.0% ‏من متطلب ‏OWASP ‏600k)
ضمن ميزانية ‏CPU ‏للخطة المجانية (‏10ms)؛ عند ‏50,000 ‏= ‏12ms ‏(فوق
الميزانية)؛ عند ‏600,000 ‏= ‏141ms ‏(‏14× ‏فوقها — الطلب سيفشل بحد ‏CPU).
‏Argon2id/scrypt ‏عبر ‏WASM ‏محظورة في ‏workerd ‏(ترجمة ‏WASM ‏وقت التشغيل
ممنوعة) وتكلفتها المحلية ‏24–60ms ‏أيضًا فوق الميزانية. الخلاصة الموثّقة:
لا خوارزمية متاحة تبلغ متطلب ‏OWASP ‏على الخطة المجانية — حدّ منصة، لا اختيار.

| المسار | تأثير ‏KDF ‏الفعلي |
| --- | --- |
| تسجيل جديد بكلمة مرور | **مغلق أصلًا** (‏503 ‏SIGNUP_DISABLED) — ‏KDF ‏لا شأن له |
| دخول حساب قائم بكلمة مرور | يعمل: التحقق بتكرارات التجزئة المخزَّنة (‏~7ms ‏عند ‏30k)، وترقية صامتة عند تغيّر السياسة |
| تغيير كلمة المرور | يعمل بنفس التكلفة؛ سياسة كلمة المرور (‏12+ ‏حرفًا، قائمة الشائع) قائمة |
| دخول ‏Google ‏(جديد/قائم) | **بلا اشتقاق كلمة مرور** في الحالة المستقرة؛ عند إنشاء الحساب تُشتق بصمة عشوائية غير قابلة للاستخدام وتُرمى فورًا (تكلفة ‏~7ms ‏مرة واحدة) |
| غياب/قصر ‏PASSWORD_PEPPER | **كل المصادقة ‏503** ‏(فشل مغلق في ‏4 ‏مواضع: تسجيل/دخول/تغيير/‏OAuth) — هذا هو السر الحرج للإطلاق، لا التكرارات |
| بوابة ما قبل النشر | تبقى ‏BLOCKED ‏(خروج ‏2) ‏بسبب ‏KDF ‏بعد اكتمال قيم الإنتاج — **الحالة المقبولة الموثّقة**، لا عطل. لا تُرفع التكرارات إلى ‏600k ‏(ستكسر الدخول)، ولا تُخفَّف البوابة لتبدو خضراء |

الخطر المتبقي بصدق: ‏30k ‏هي ‏5% ‏من مستوى ‏OWASP ‏ضد كسرٍ دون اتصال لقاعدة
مسرَّبة؛ التخفيف القائم: الـpepper ‏(فصل نطاقي ‏HMAC — قاعدة مسروقة وحدها
لا تكفي دون السر الخارجي) + سياسة كلمة مرور قوية + حدود معدل/قفل تخمين.
الرقم الملزم مستقبلًا من ‏`wrangler tail` ‏بعد أول نشر، لا من القياس المحلي.
